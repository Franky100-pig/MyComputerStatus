**The reboot was clean, and that closes an open item.** On 11-02 this log recorded that the

`Successful logout so clear the previous startup was a panic value` at **21:24:17**, 18 seconds

**One operational correction about the diagnostics store, and it is a useful one.** **Ten of the
eleven** `.diag` files across both stores carry mtime **22:44–22:45** — right when the machine woke
from its 10-hour sleep — while the events *inside* the same files are timestamped **07:43 →
09:01**. The store is flushed to disk **at wake**, up to 13 hours after the event it describes. So:

- a file's **mtime** answers "when was this written", not "when did this happen";
- a run that samples right after a wake sees a **burst of files describing the previous awake
  block**, not the last 24 hours;
- counting a store by mtime therefore over-counts whatever the last wake flushed. Count by the
  inner `Date/Time`, and state which one is being quoted.

This supersedes the vaguer version of the same rule ("the store's mtime bounds the count"): the
mtime bounds *when the count arrived*, not *what the count covers*.

**New rule for future runs:** *record the clone's parent mtime and the inner bundle version, and
treat the pair as identity.* A version string alone cannot distinguish a 5-day-old copy from a

### 2.3 The write-budget instrument finally answered — 18.5× over budget

The `com.apple.SystemStats.Daily.IO` report for 11-06 19:09 → 11-07 19:09 contains one triggered
event, and it is the largest this log has ever read:

| Attribution | one system **web-engine network helper**, running on behalf of a third-party desktop app (category: an embedded-browser app) |

Three things follow, and the third is the one that matters:

1. **The budget is a 24-hour byte cap, not a rate alarm.** 2 147.48 MB / 86 400 s = 24.86 KB/s,
   and the process dirtied 2 147.49 MB — it hit the cap **to the byte**, exactly as the two
   processes on 11-03 did. A process that writes hard for 78 minutes can burn a full day's
   allowance and then be silent. So "no second report today" is *not* evidence that nothing else
   wrote.
2. **This is the first gross-write number in the right magnitude for the mystery.** The
   unexplained disk moves this log has chased were +1.1 to +2.1 GB/day. Today one app produced
   **2.1 GB of dirtied file-backed memory in an hour and a quarter** — on a morning the machine
   was otherwise mostly asleep.
3. **It did not become disk growth.** The same 24 hours ended with used space **down 1.84 GB**.
   Dirtied file-backed pages are **overwrites in place**; they cost write endurance and battery,
   not free space. So the correct conclusion is not "the leak is this app" — it is that **the
   disk's net delta is set by reclamation (clone release, purgeable, snapshots), not by write
   volume**, and that this log has been measuring the wrong quantity for the wrong question
   since 10-30.

**What this costs the SSD — little, and the arithmetic says why.** The pack-side detail does not
matter here; the drive does. 2.1 GB is **0.46 % of the 460 GB volume** in one burst, and even at
*one such burst every day for five years* it totals ~3.8 TB of host writes, an order of magnitude
below the endurance rating of any SSD Apple ships in this class. So the write budget is a
**battery-and-latency** instrument, not an endurance alarm. What it is genuinely good for is
naming the writer — which it did today, for the first time in 30 reports.

The daily aggregate report for the same window sampled **471 of 472 write samples** from that one
process, so there is no second writer of comparable size anywhere in the 24 hours. That is a much
stronger statement than "no other report fired": the sampler's own distribution agrees.

## 5. Swap — a 07:44 cycle that kills the "evening timer" theory

| Metric | Value |
|---|---|
| Pool | **0 MB** (`total = 0.00M used = 0.00M`) |
| Files on disk | **0** |
| `Swapins` / `Swapouts` since boot | **0 / 0** — literal zeros |
| VM volume directory mtime | **2026-11-07 07:44** |

The directory is **empty**, so this is a **create-and-release cycle**, and its mtime says the
whole cycle completed inside one minute at **07:44**.

- **07:44 is 24 seconds after the diagnostic window opened at 07:43:38** and 3 minutes after the
  machine woke at 07:41:38.
- Previous cycles were recorded at **22:39 (10-28), 22:35 (10-30), 20:39 (11-03), 21:46
  (11-05)** — four evenings running, which is why 11-04 and 11-06 concluded "housekeeping on a
  timer, not pressure response".

**07:44 is not an evening, and the theory does not survive it.** A timer does not fire 8 hours
early after a reboot; an app launch does. Two facts now fit the same explanation:

1. the cycle lands **seconds after the biggest process launch of the day**, and
2. **not one page was ever written to the file** — `Swapins` and `Swapouts` are still literally
   `0`, so the volume was allocated and released without a single fault going to it.

That is the signature of an **allocation probe**: macOS reserves swap headroom when commit charge
spikes, then gives it back when pressure never materialises. The evening cycles of 10-28 → 11-05
were therefore probably evening *app launches*, not a cron. **Revised rule: date the swap cycle
against process launches, not against the clock, and require a `Swapins`/`Swapouts` delta before
calling any swapfile "used".** The 10-30 report's real outflow (102 084 pages) remains the only
evidence in the series that a swapfile ever held data.

The 11-04 conclusion that the cycle is "housekeeping on a timer, not pressure response" is
**half right and half wrong**: it is not pressure *in traffic terms*, but it is pressure-triggered
in *allocation* terms, and it is not on a timer.

### 6.3 The gap: there is no "average RAM" instrument

**The request behind this log is "average RAM consumption", and this report cannot measure it.**
What exists is a snapshot (9.53 GB at 22:47) and two historical points (11.12 GB on 11-06,
10.82 GB on 11-04). There is no sampler: `vm_stat` is instantaneous, the `memorystatus` kernel
records carry sizes only at kill events (one today), and the diagnostics store carries no memory
series. Quoting a snapshot as a daily mean would be exactly the mistake this log exists to

**Best available estimate, labelled as an estimate:** with one boot, one 171-minute working

settled 9.53 GB — call it **~7–9 GB (45–58 %)**, midpoint ~8 GB. Method: a ramp between the
post-boot floor and the settled reading, which is a *model*, not a measurement. **Top forward
item is to instrument this properly** (§11, item 1).

boot**. It fired 19 seconds after the kernel came up, with **93.5 % of RAM free**, killing the
crash reporter itself while it processed the shutdown's backlog. That reclassifies the class:

- **`per-process-limit` with ≥ 1 GB available is a cap defect, and the frequent ones are
  boot-time.** The 11-03/11-05 specimens (15 MB indexing daemon, 8.4–8.7 GB free) and today's
  (114 MB crash reporter, 15.0 GB free) share nothing except that a small daemon briefly
  exceeded a fixed cap while nothing was short of memory. None is pressure; none needs action.
- **The genuine-pressure variant stands** (11-02: `available_pages: 59` = 0.9 MB). That one is
  distinguishable by the availability figure alone, which is why 11-03's rule to always quote the
  pair is the right one.
- **New:** a boot-time kill is not evidence about the *day*. Check the timestamp against
  `kern.boottime` before attributing a kill to the workload.

### 7.3 Zero idle-exit reaps — the 11-06 "timer" claim is falsified

| | 11-06 (its window) | **11-07 (26 h)** |
|---|---|---|
| `killing_idle_process` | **535** | **0** |
| `killing_specific_process` | 1 | 1 |
| Total `memorystatus` lines | 1 209 | 150 |

11-06 recorded 535 idle-exit reaps arriving in **14 bursts capped at 60/minute**, 30 minutes
apart, and concluded they came from a **timer rather than a wake side-effect**. A timer would
have fired today. It did not fire **once in 26 hours**. So the bursts are **not clock-driven**;
the only variable that changed is the boot (daemons reaped on 11-06 had been idle 10 000–15 000 s,
i.e. they were old), which points at **daemon age / accumulated idle state**, not a schedule.
Recorded as a falsification, with the 11-06 mechanism downgraded to "unknown trigger, correlated
with uptime".

Also worth noting for future censuses: **5 non-fatal soft-limit notices** appeared, all from Apple
system daemons (a file-provider agent, a search-index agent, the metadata indexer, a
background-sync agent and a dedup agent) at soft caps of 15–100 MB; one landed at **07:50:40 —
inside the working session**. These are `exceeded mem limit: … (non-fatal)` and they never kill
anything. **They are not kills and must not be counted with them** — a third class to keep
separate from `killing_idle_process` and `killing_specific_process`.

## 9. The perturbation — and why the load reading is not a finding

No second collector pass was taken this time, and that is a deliberate change: on 11-03, 11-04 and
11-06 the post-work reading cost 3–5 battery points and every time confounded the day's verdict
with the measurement. Today the machine was **on AC from 22:43:45**, so the sweeps were free.

| Sweep | Window | Cost |
|---|---|---|
| `powerd`, 26 h | 39 939 lines | free (AC) |
| `memorystatus`, 26 h | 150 lines | free (AC) |
| Panic predicate, 26 h | 117 lines | free (AC) |
| Store walk + clone walk | — | free (AC) |

**Load 5.68 at the sample is a transient, and one extra reading proves it.** Eight minutes later,
at **22:54:58**, the same machine read **1.35 / 2.02 / 2.33** — the 1-minute average fell by 76 %
and the **15-minute average fell too** (2.88 → 2.33), which can only happen if the recent minutes
were far quieter than the quarter-hour before the sample. The 22:47 reading is therefore **wake
catch-up**: the machine had been asleep for 10 h 17 m, woke at 22:42:58, and four minutes later
was still faulting pages back and flushing the diagnostics store (§1).

Recorded as a rule rather than an anecdote: **a load average taken within ~5 minutes of a wake
does not describe the day**, and this log has been quoting such readings in the CSV for weeks.

The CSV row keeps the **22:47:07** value because that is the comparable pre-work sample, and
because plugging in happened only 4 minutes earlier, so the row is the **last honest on-battery
reading** (85 %) rather than a charge-inflated one. The 22:54 load is quoted here as the
correction rather than rewritten into the row — changing a logged sample after the fact is how a
history stops being a history.

## 10. Comparability warning

| Metric | Why it must not be compared across this boundary |
|---|---|
| RAM used, compressor | **1-day boot.** The compressor goes 5 GB → 1.7 GB on restart; any day-over-day delta is the boot, not the workload |
| Compression churn | Same — cumulative since boot, and 85 % of the window was asleep. Use per-awake-hour (§6.2) |
| Sleep census | Window is 25.4 h here, 58 min on 11-06, 48 h on 11-04. Only the *share* is comparable |
| Disk | Reboot released 1.4 GB of clones; the 3 GB band is the honest comparison, not the daily delta |
| Kill counts | `idle-exit` reaps appear only after daemons age; a fresh boot has none |

## 11. Forward conditions

1. **Instrument the RAM mean.** Add a sampler (a 15-minute `vm_stat` append to a local file, not
   into the repo) so the next report can quote a real daily mean instead of a bounded estimate.
   This is the one metric the user has asked for repeatedly that the log still cannot produce
   (§6.3).
2. **Date every swap cycle against a process launch**, and stop calling the evening appearances a
   timer. Require a `Swapins`/`Swapouts` delta before saying a swapfile held data (§5).
3. **Quote `per-process-limit` kills with `kern.boottime` next to them.** A kill 19 s after boot
   with 15 GB free is a boot artifact; the same reason string during a working session with
   0.9 MB free is an incident (§7.2).
4. **Three kill classes, always counted separately:** `killing_idle_process`,
   `killing_specific_process`, and non-fatal `exceeded mem limit` soft notices (§7.3).
5. **Check `UPTIME_DAYS` before making any claim**, and lower confidence when it is large (§8).
6. **Count diagnostics by inner `Date/Time`, not mtime** — the store flushes at wake (§1).
7. **Read the write-budget report the day it appears, and read the `Duration Sampled` line with
   it.** 93 % sampling made today's claim possible; a 12-hour window would not have (§2.3).
8. **Bluetooth test still open** (11-06 item, untested for 2 runs): peripheral off in the bag →
   does mean sleep exceed 2 min? The 35-minute blocks here are unexplained, not evidence (§4).
9. **Next boot test:** is the 1.6 GB clone released if the browser is *quit* without a reboot?
   That distinguishes "cache with reboot lifetime" from "cache with process lifetime" (§2.2).

## 12. Method

```bash
# snapshot (anonymous, no sudo) — the CSV row comes from this and nothing else
bash scripts/collect.sh > /tmp/mcs_snapshot.txt
python3 scripts/append_csv.py < /tmp/mcs_snapshot.txt   # NOT a second collect.sh run

# battery curve — /usr/bin/log, never bare `log` (zsh builtin shadows it)
/usr/bin/log show --last 26h --predicate 'process == "powerd"' --style compact > /tmp/powerd.log
grep -a "Battery capacity change posted" /tmp/powerd.log | grep -a "Capacity:" \
  | sed -E 's/^([0-9-]+ [0-9:]+).*Capacity:([0-9]+).*Source:([A-Za-z]+).*/\1 \2 \3/'

# sleep/wake — pair each sleep entry to the next wake, then MERGE the intervals; a sleep can be
# followed by several dark wakes and the raw pairing is not trustworthy until merged. This run
# also needs `Entering Sleep` AND `Sleep Service Back to Sleep` or 53 blocks go missing.

# kernel census
/usr/bin/log show --last 26h --predicate 'process == "kernel" AND eventMessage CONTAINS[c] "memorystatus"' --style compact

# disk: clone tree, snapshots, write budget
find /private/var/folders -maxdepth 6 -type d -name "*.code_sign_clone"
diskutil apfs listSnapshots /System/Volumes/Data
grep -a "^Writes: " "/Library/Logs/DiagnosticReports/disk writes_<ts>.diag"
grep -a "^Duration Sampled: " "/Library/Logs/DiagnosticReports/disk writes_<ts>.diag"
```

Data sources are read-only. Nothing in this report was written from a process list, and the
per-process attribution that produced §2.3 was reduced to **category** before publication.

`data/history.csv`.*
