| Zero-byte dirs | 1 | 1 | 5+ | **at least 3, from 3 different apps** |

Two readings, both useful:

1. **The filled clone is back to 1.10 GB** — exactly the size it reported on 11-08 and 11-09 — with
   **mtime still 11-08 13:04:48**, i.e. *nothing was written to it in three days*. The 0.70 GB
   reading on 11-10 was the `du`-on-CoW artefact this log already suspected, not a decrease. **Stop
   quoting the filled-clone size as a number; quote the mtime.** Unchanged mtime plus unchanged
   app version = no growth, regardless of what `du` says.
2. **A new zero-byte clone directory appeared at 11-10 09:50:06**, belonging to a different app,
   and it is empty. That is the third distinct app to leave one. The pattern is now clear enough to
   state: **launching a code-signed app can leave an empty `code_sign_clone` directory that is
   never cleaned up.** They are inert (0 bytes each), so this is a **directory-count** curiosity,
   not a disk problem — and it is the reason §6.2's counts must never be read as sizes.

**So +0.98 GB stays unattributed**, for a third interval, because the write-budget report lives in
the store that is missing (§1). The clone tree cannot explain it: its mtime says it wrote nothing.

## 7. Anomalies — zero panics, one capped daemon, and four Wi-Fi fault reports

### 7.1 Zero panics; one kill, and the reason string is the whole story

The diagnostics store is gone (§1), so all of this comes from the kernel's own log — **99 matched
`memorystatus` lines** over the interval.

| Class | Count | Reading |
|---|---|---|
| **Panics** | **0** | the kernel predicate returned the header row only |
| **Kills total** | **1** | `per-process-limit`, a daemon exceeding its own cap |
| Available pages at the kill | **585 685 = 9.6 GB** | ⇒ **not** exhaustion |
| `idle-exit` reaps | **0** | consistent with the compressor never leaving the 5.2–6.3 GiB trigger zone (§5.3) |
| **Pressure / critical / highwater** | **0** | none in the interval |
| Non-fatal "exceeded mem limit" notices | **11** | all `ActiveSoft` / `InactiveSoft` caps of 15–80 MB — advisory, not kills |

The one kill is the known configuration defect, and today's instance is textbook: **15 600 KB of a
daemon against a soft cap, with 9.6 GB available.** The 11-02 rule applies unchanged — *`per-process-limit`
with ≥ 1 GB available is a cap to ignore; the same kill with ≤ 100 pages is real pressure.* This is
the former, at 96× the boundary.

**And the reaps are simply absent today**, which is the quietest crash column since 11-07 (0 reaps).
A day with no housekeeping burst, no pressure event and no panic is what a healthy machine looks
like when nothing has been asked of it.

### 7.2 New: four wireless firmware fault-report callbacks, all benign

The kernel logged **four** `completeFaultReportCallback … watchdog result 0` events from the Wi-Fi
driver — 11-10 11:05:59, 17:27:11, 23:20:42, 11-11 07:36:42. **`result 0` means no watchdog fired**,
so these are the driver's routine fault-report plumbing running, not resets the user could feel.

Recorded because this log has not counted them before and they are now on the "how often" baseline:
**four in 24 h.** If that number climbs into the tens, or if a `result` other than 0 appears, it
becomes a real finding. Until then it is noise with a known shape.

### 7.3 Noise predicates to keep ignoring

The bare `jetsam` predicate stays useless (73 631 lines of running-board chatter on 11-09).
`process == "kernel"` + `eventMessage CONTAINS "memorystatus"` remains the only combination that has
produced a usable count, and today it produced one line worth reading out of 99.

**One new tooling trap, recorded because it cost this run two empty files:**

```
$ log show --last 5m --predicate 'process == "powerd"'
(eval):log:1: too many arguments
```

**`log` is a zsh builtin in this shell.** The daily sweep must call **`/usr/bin/log`** explicitly, or
it silently produces nothing and the coverage table looks like an instrument failure. Both log
sweeps in this report were re-run with the absolute path.
