### 6.2 Two per-process-limit kills — and one of them is not a configuration defect

| Time | Process category | Size | **Available pages** | Reading |
|---|---|---|---|---|
| **11-02 10:57:05** | system content-indexing daemon | **15 392 KB** | **637 122** (9.7 GB) | **the known defect**: a 15 MB daemon killed while 9.7 GB was free |
| **11-02 10:58:08** | system intelligence-platform service | **20 528 KB** | **59** (0.9 MB) | **not the defect**: the machine had nothing left at that instant |

Both fired inside a **63-second** span, an hour after the previous report's sample, which is why
neither had been seen.

**This breaks the 10-28 reclassification.** That rule — "per-process-limit is a configuration defect,
stop counting it as a crash" — was built on four events that all had **7.5–8.6 GB available**, and
it generalised from the reason string. Today the same reason string appears with **59 available
pages**, which is not a cap being too low; it is a **genuinely exhausted machine**. The rule needs
the availability number attached, not just the reason:

> A `per-process-limit` kill with **≥ 1 GB available** is a cap defect (`Action: ignore`).
> The same kill with **≤ 100 pages available** is real pressure (`Action: investigate`).

The second kill also sits **one minute** after the first, which raises an ordinary alternative worth
stating: the first kill may have *created* the pressure, or both may be consequences of the same
minute-long spike. The counters cannot separate those — `memorystatus` is sampled, not logged
continuously — so this is recorded as **one pressure episode with two kills**, not two episodes.

**Load was not the story either:** the sample 22 hours later reads **1.46 / 1.54 / 2.13** with
**10.83 GB / 67.7 %** used and **zero swap**. Whatever happened at 10:58 on 11-02 left no residue in
any state meter — which is itself the point: **a one-minute exhaustion is invisible to a once-daily
instantaneous sample, and visible only in the kernel log.**

## 8. Forward conditions

1. **Clone tree — switch from bytes to version.** The 1.6 GB/day projection is falsified (§3.2). Check
   **the browser's version string** at each run instead: a new clone should appear **only** when that
   version changes. If a clone appears with an unchanged version, the "per update" story is wrong.
2. **Compression churn at ~3 days uptime.** The test is now sharper than "does it climb": measure
   **compressions per page-in** at ~3 d. If the ratio keeps rising (0.74 → 1.85 → ?) while page-ins
   stay near 2.5 M/day, uptime dependence is settled and the machine's real problem is **long
   uptimes**, not workload.
3. **The pressure episode of 11-02 10:58.** One minute, 59 available pages, two kills, zero state
   residue. Watch for a **third** occurrence and for whether it lands near 10:57 again — a fixed
   hour would point at a scheduled job, a random hour at genuine workload. Nothing to do until then.
4. **Read the write-budget reports every run.** They are the only instrument in this repo that
   measures **writes**. If a process sustains ≥ 40 KB/s again for hours, that is the answer to
   "what grows the disk" and it should be named by category in that day's §2.
5. **Read `per-process-limit` with its availability figure** (§6.2). ≥ 1 GB available → defect,
   ignore. ≤ 100 pages → investigate. Never generalise from the reason string alone again.
6. **Power-log rotation is the binding limit, not the schedule.** 11-02's daylight hours are gone and
   with them a 33-point discharge. Every battery section must state its window explicitly, and a
   `DailyMinSoc` that cannot be explained inside the window should be read as **"outside coverage"**
   first (§5.3).
7. **`jetsam_24h` in the CSV is a file count.** It read 0 against 2 real kills. Do not tighten the
   schema mid-series; do label it in the README if this ever gets charted.

## 9. Method

`bash scripts/collect.sh` for the published row (sysctl / vm_stat / pmset / df / diskutil only, no
sudo, no identifiers), plus, for this report only: `sysctl kern.boottime kern.shutdownreason`,
`vm_stat` (counters), `pmset -g log` (rotated store, 2 921 lines, **11-02 22:04:39 → 11-03 08:21**),
`pmset -g custom`, `ioreg -c AppleSmartBattery`, `diskutil apfs listSnapshots`,
`tmutil listlocalsnapshots`, `du -xh -d1 /private/var/folders`, `find` on the clone tree,
`ls -ld` on the diagnostics store **and both of its parents**, the two `.diag` files read in full,
and `log show --last 24h` with predicates for `panic`, `memorystatus`, `killing` and
`per-process-limit` (store verified to reach back to **11-02 08:33:21**).

Per-boot temp-tree paths and clone directory names embed **application names** and are therefore
reported as **"a browser's per-update code-sign clone"**; the two `.diag` files name their processes,
their paths and the host name, so they are reported as **"a browser helper"** and **"a system
file-copy utility"**, with only their event class, window, rates and sizes published. Diagnostic
file names are counted, never printed. All per-24-h figures are **uptime-normalised or
interval-derived**, never extrapolated from one instantaneous sample.
