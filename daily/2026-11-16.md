Yesterday's conclusion was that 336 MB of swap was *"cold pages parked on disk"* that would
sit there until reused. Today it was reused hard, and the mechanism is visible:

1. Swap used **> pool size** at 18:19 (5 309 MB against a 3 072 MB pool today) means the pool
   was **larger then** — at least 5 310 MB, i.e. at least six 1 GiB files — and macOS has since
   **reclaimed files**, leaving three. This is dynamic swap resizing in both directions, not a
   one-way ratchet.
2. **8.34 GiB out and 5.99 GiB back in** in 24 h. The system moved thirty times more data to
   disk today than it had in the entire boot history before it.
3. The drain is steady and ongoing: 5 309 → 3 870 → 3 131 → **1 749** MB across the following
   17 hours, in even steps of 40–60 MB per 15-minute sample. That is the system returning cold
   pages on demand, not a new burst.

**The 11-15 report's "rename the swap column" question is now answered — keep the name.** Swap
in this log does mean pressure; it just means it rarely.

No swapfile creation event appears in the unified log (searched explicitly for the string
`swapfile`: one hit, the search's own argv). File **mtime is the only evidence**, which is why
the 11-15 report could only bracket the event to a minute. Today's bracket is one second.

1. **Every burst began with 3.9–6.4 GiB available.** That is *plenty* of memory by any

2. **Bursts 1, 2 and 3 all started between 6.06 and 6.39 GiB available.** Three consecutive

The hypothesis from 11-15 — "bursts follow a state change with a large idle population, not a
level" — survives and is strengthened. Burst 3 did not follow a level at all: the level was
being *consumed* while the burst ran.

**Status:** 🟢. Yesterday's report marked the reap threshold 🟡 because it had falsified a

single most memory-stressed hour in the log's history is evidence the reaper is **not** a

### 7.2 The 91 % peak is the headline, and it is not an anomaly

A machine that reaches 91 % RAM looks alarming in a table. It should not here:

- **0** processes were killed for capacity.
- **0** memory-pressure warnings were recorded.
- The system responded by **adding swap**, which is the designed behaviour.
- The peak lasted **minutes**, not hours: 14.56 GB at 18:19:39, 9.35 GB fifteen minutes later.

The correct reading is "a 7B parameter model was loaded into a 16 GB laptop", which is a
workload statement, not a health statement. The log should record the peak — and should not

### 7.3 The `panic` filter needed one change this run

Six hits, **all** of the same benign shape:

```
2026-11-15 17:02:44  kernel  (Sandbox) Sandbox: softwareupdated deny(1) nvram-get panicmedic-auxkc-present

```

The unified search today was scoped to `process == "kernel"`, which **excludes the reader's
own argv** — the fourth recurring false positive from previous reports did not appear. That is

probing `nvram` keys whose names contain the word.

### 7.4 What the nine `.diag` files probably are

`SFA-` records are written when a sysdiagnose-style capture fails to complete. Eight of the
nine were written inside **40 seconds** at 10:45, covering eight different subsystems
(keychain, networking, secure-transport, root-networking, …). That pattern — every subsystem
attempted at once, none completed — is what a **stress-triggered diagnostic attempt** looks
like, and 10:45 is inside the window where the battery was charging and the machine was busy.

It is not evidence of a fault. It is evidence that something *asked for a full diagnostic* and
could not produce one. Worth recording because it recurs and because the collector was
silently reporting zero.
