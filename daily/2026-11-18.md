**The first pass of this table was wrong, in an instructive way.** It reported 23 957 / 13 688 /
30 224 / **1** / 31 947 / **1**, and the two ones read as "nothing logged for half an hour, the
machine must have been asleep". They were my own bug, twice over:

| Mistake | What it did |
|---|---|
| `--end "$w:30"` | zsh appends the literal string `:30`, so the window was **30 seconds**, not 30 minutes — hence the small counts |
| `--end "2026-11-18 03:30"` (no seconds) | `log show` **rejects** it — `Failed conversion … using format '%Y-%m-%d %H:%M:%S'` — and returns **zero rows** |

Both were invisible because the probe ran with `2>/dev/null`, which threw away the conversion
error. A `log show` that fails argument parsing prints nothing on stdout and exits non-zero, and
the result is indistinguishable from a valid query over a silent machine. **Always pass full
`HH:MM:SS` on both ends, and never silence stderr on a query whose emptiness you are about to
interpret.** This is the third member of the same family as 11-15's `panic` predicate matching
its own argv and 11-17's zsh `log` builtin: the query looked fine, the answer was empty, and the
emptiness was the bug.
